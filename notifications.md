# Notification System


The Notification system is a shared service used by every module. It receives events from the other modules, turns them into messages from templates, and sends them to customers by push, e-mail or SMS. Customers choose on which channels they receive each type of message. Security messages are always sent.

Module boundaries:

- The Notification system never decides on its own what to send. It only reacts to events. If a module needs a new message, it publishes a new event, and a template for that event is added here.
- One-time confirmation codes are generated by CBS. The Notification system only delivers them.
- The content of a message comes from the event payload. The Notification system does not read other modules' data.

The push service, e-mail provider and SMS provider are external systems. They are described as one interface in section 7, so they can be replaced with mocks during implementation.

## 1. Feature list

| ID | Feature | Actor | Priority |
|---|---|---|---|
| NTF-01 | The system sends a notification for every event in section 7 that has a template. | System | Must |
| NTF-02 | A notification is in the user's language (LT or EN). If no template exists in that language, the English one is used. | System | Must |
| NTF-03 | A notification that is not mandatory is sent only through the channels the customer enabled for its category. | System | Must |
| NTF-04 | Security notifications are always sent, even if the customer turned off every channel. One-time codes are sent only by SMS. | System | Must |
| NTF-05 | If delivery fails, the system tries the next channel in the order push, SMS, e-mail, with at most 3 attempts in total. | System | Must |
| NTF-06 | A notification never contains a full card number, a password, or the reason AML rejected a payment. | System | Must |
| NTF-07 | The customer turns push, e-mail and SMS on or off for each category except Security, and chooses the language. | Customer | Must |

Templates are loaded from the starting set in section 7. There is no screen for editing them.

## 2. Business flows

Changing the settings (NTF-07) is a simple action and is described only in the wireframes.

### F1. Send a notification

Actors: the module that publishes the event, the Notification system, the channel provider, the Customer.

Preconditions: a module has published an event listed in section 7.

Basic course:

1. The Notification system receives the event, for example TRANSACTION_COMPLETED.
2. The Notification system reads the userId from the event payload and loads the User's language (LT or EN).
3. The Notification system loads the NotificationTemplate for the event type, variant and language, and fills in the placeholders from the payload.
4. The Notification system loads the User's NotificationPreference for the template's category and picks the first enabled channel, in the order push, SMS, e-mail.
5. The Notification system saves a Notification with status PENDING and sends it to that channel's provider.
6. The provider returns DELIVERED. The Notification system sets the Notification status to DELIVERED.
7. The Customer receives the message.

Alternate courses:

- A1. The template is mandatory. At step 4, the Notification system ignores the NotificationPreference and uses push, then SMS. For OTP_REQUESTED, it uses only SMS.
- A2. The provider returns FAILED or does not answer within 30 seconds, or the User has no push token. The Notification system tries the next channel in the order push, SMS, e-mail. After 3 failed attempts in total, it sets the status to FAILED and publishes NOTIFICATION_FAILED.
- A3. The Customer turned off every channel for this category. The Notification system sends nothing and saves no Notification.
- A4. No NotificationTemplate exists in the User's language. The Notification system uses the English template.

## 3. Non-functional requirements

These apply to this module. The requirements common to the whole system are in the Non-functional requirements chapter.

| ID | Requirement |
|---|---|
| NTF-NFR-01 | 95% of notifications are handed to the provider within 10 seconds after the event. For mandatory notifications, the limit is 5 seconds. |
| NTF-NFR-02 | Every event is processed at least once. An event with an eventId that was already received does not create a second notification. |
| NTF-NFR-03 | A slow or unavailable provider does not slow down the module that published the event. |

## 4. High-level architecture

The module consists of these packages. The package and class diagrams for the whole system are in the Architecture chapter.

| Package | Responsibility |
|---|---|
| notification.dispatch | Listens to events, picks the template and channels, and handles retries on another channel. |
| notification.templates | Stores templates and fills in placeholders. |
| notification.preferences | Stores customer channel preferences and provides the settings endpoints. |
| notification.channels | One adapter per channel (push, e-mail, SMS) that implements the provider interface in section 7. |

## 7. API contract

All endpoints use JSON. Times are in ISO 8601 UTC, for example "2026-10-11T10:42:00Z". Errors use the common error body with code and message.

Customer endpoints need a customer token and only return that customer's data.

### Customer endpoints

| Method and path | Purpose | Request body | Success response | Errors |
|---|---|---|---|---|
| GET /api/v1/notification-preferences | Get the settings | none | 200, list of category with pushEnabled, emailEnabled and smsEnabled, plus language | |
| PUT /api/v1/notification-preferences/{category} | Change one category | pushEnabled, emailEnabled, smsEnabled | 200, the saved row | 422 CATEGORY_NOT_EDITABLE for SECURITY |
| PUT /api/v1/notification-preferences/language | Change the language | language | 200 | 422 VALIDATION_ERROR |

### Event format

Every event in the system uses the same envelope:

```json
{
  "eventId": "uuid",
  "eventType": "TRANSACTION_COMPLETED",
  "occurredAt": "2026-10-11T10:42:00Z",
  "source": "payments",
  "payload": { }
}
```

If the same eventId is received twice, the receiver ignores the second one.

Events the Notification system receives. The payloads must match what the owning modules publish.

| Event | From | Payload fields used | Mandatory |
|---|---|---|---|
| TRANSACTION_COMPLETED | Payments | userId, transactionId, amount, currency, direction, counterpartyName | no |
| TRANSACTION_REJECTED | AML | userId, transactionId | yes |
| CARD_TRANSACTION_AUTHORIZED | Cards | userId, transactionId, cardLast4, amount, currency, merchantName | no |
| CARD_BLOCKED | Cards | userId, cardId, cardLast4 | yes |
| KYC_APPROVED | KYC | userId | yes |
| LOAN_INSTALLMENT_DUE, LOAN_INSTALLMENT_MISSED | Loans | userId, loanId, amount, dueDate | no |
| OTP_REQUESTED | CBS | userId, code, purpose | yes, SMS only |
| NEW_DEVICE_LOGIN | CBS | userId, deviceName, city | yes |

Events the Notification system publishes:

| Event | Payload | Who reacts |
|---|---|---|
| NOTIFICATION_FAILED | notificationId, userId, eventType | Audit log |

### Provider interface

This can be a mock during implementation.

Each channel adapter implements send(recipient, title, body) and returns DELIVERED or FAILED. The recipient is a push token, an e-mail address or a phone number. The mock can be set up to fail a given share of messages, so the fallback in F1 can be tested.

### Starting templates (EN)

| Event | Category | Mandatory | Title | Body |
|---|---|---|---|---|
| TRANSACTION_COMPLETED (INCOMING) | TRANSACTIONS | no | Payment received | You received {amount} {currency} from {counterpartyName}. |
| TRANSACTION_COMPLETED (OUTGOING) | TRANSACTIONS | no | Payment sent | {amount} {currency} was sent to {counterpartyName}. |
| CARD_TRANSACTION_AUTHORIZED | CARDS | no | Card payment | {amount} {currency} at {merchantName}, card ending {cardLast4}. |
| TRANSACTION_REJECTED | SECURITY | yes | Payment not executed | Your payment could not be executed. Please contact the bank. |
| CARD_BLOCKED | SECURITY | yes | Card blocked | Your card ending {cardLast4} has been blocked. |
| OTP_REQUESTED | SECURITY | yes | Confirmation code | Your code is {code}. Never share it with anyone. |
| NEW_DEVICE_LOGIN | SECURITY | yes | New login | New login from {deviceName} in {city}. If this wasn't you, block access in the app. |
| LOAN_INSTALLMENT_DUE | LOANS | no | Installment due | {amount} EUR is due on {dueDate}. |
| LOAN_INSTALLMENT_MISSED | LOANS | no | Installment overdue | Your installment of {amount} EUR is overdue. |
| KYC_APPROVED | SECURITY | yes | Account verified | Your identity has been verified. You can now use all services. |

TRANSACTION_COMPLETED has two templates, and the direction in the payload decides which variant is used. The LT versions use the same placeholders.

TRANSACTION_REJECTED never says why the payment was rejected. This is required by AML law (see the AML chapter, F2).
